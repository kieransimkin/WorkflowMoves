## Fresh chat recovery for a closed browser transport

Use this route only when the documented browser execution tool returns `Transport closed`, a supported kernel reset cannot execute, and the user explicitly requests or approves moving this task to a fresh chat. A visible signed-in page alone does not prove tool access.

1. Preserve the current task's ledger, completed actions, pending targets and exact verification gaps. Use read-only checks to establish that any previously reported capacity or path fault is currently resolved; do not infer that from another chat's success.
2. Do not stop browser helpers or terminate, restart or force-stop Codex. A helper process belongs to an app-managed connection; stopping it can close the connection without creating a replacement. Do not change credentials, protected paths, access controls or unrelated settings.
3. With the user's explicit authorization, use the supported same-directory chat fork. After an interrupted or uncertain fork, inspect current chats before creating another. Carry forward a concise task prompt that names current artifacts, completed work and the remaining authorized action.
4. In the fresh chat, follow the current Browser skill and connect through its documented runtime. Select the existing matching tab and inspect its current contents. Never inherit an old JavaScript handle or reuse a stale accessibility index. If native element targeting reports stale or missing elements despite a fresh tree, use another documented interaction grounded in current visible state.
5. Verify the previously failing operation itself, then finish the original authorized task. Distinguish a fresh chat's working authenticated read from restoration of the old chat's transport. Reconcile any recurring automation's actual target after a fork; preserve its schedule, prompt and notification preferences.
6. Retain dated recovery evidence and the exact remaining verification limits. The fresh chat is a recovery route for an explicitly requested task, not permission to wake or resume other chats.

### Potential problems

A kernel reset cannot repair a closed app-managed transport. Repeated calls returning `Transport closed` do not establish a platform sign-out or a new browser failure. The original chat's transport remained unverified. This validates the fresh-chat route for that condition; it does not establish the original error's cause or a universal fix.
