## Connect suitable EPK effects to mobile motion

- Standing instruction from Kieran, 11 October 2026: every EPK creation, edit, publication, shared motion upgrade, campaign review and recurring release/EPK audit must inventory pointer, hover, tilt, parallax, depth, lighting and directional effects and verify that effects suitable for phone movement have a working mobile sensor connection. Apply to past and future releases and every project chat, agent and scheduled workflow. Follow `Workflows/epk-mobile-motion.md`.
- Identify each effect's actual visual consumer, variables, bounds, acquisition owner, controller and neutral state. Check artwork, hero, below-fold cards and playback stages. A loaded plugin, listener, permission button, CSS variable or desktop mouse response alone does not prove mobile attachment. Keep static pages, ordinary button hover/focus feedback and scroll/navigation controls intentional; do not add movement solely to satisfy a checklist.
- Use the current published DanceMoves sensor/controller APIs. Bind mobile input to the same approved appearance mapping as pointer input; keep page-owned callbacks narrow. Share sensor acquisition and permission UI across related consumers. Extend an existing working route through supported subscription/composition rather than adding a competing listener, scheduler or page-specific shared-library branch. Preserve desktop pointer and keyboard/focus behaviour independently.
- Require a secure context and supported mobile/touch device. Request sensor permission only when required and only from an explicit visitor gesture; on other browsers use the supported direct-listener route. Distinguish eligible, permission requested/granted/denied, listening, finite data received and visibly active. Leave an accurate unavailable/blocked state when readings do not arrive. Never imply sensor delivery from a stored choice or permission response.
- Keep explicit page motion-off, reduced motion, forced colours, visibility, screen rotation, pagehide/pageshow, root removal and teardown authoritative. Reset pending input and visual targets appropriately; do not silently persist an opt-out when merely suspending a page or overwrite a visitor's choice on teardown. Keep input bounded, account for screen orientation and suppress stationary jitter. Preserve supported calibration/window settings unless a reviewed change is required.
- Verify fresh saved source and rendered desktop/tablet/mobile output, the full route from sensor event through controller to each required painted consumer, all motion switches, permission/denial/no-data paths, lifecycle resets and listener cleanup. Test input storms, meaningful bounds and any applicable adaptive downgrade/recovery. Label emulated or synthetic evidence accurately; physical phone/Safari behaviour and frame-rate acceptance need physical evidence. Record no unnecessary sensor route for intentionally static effects.
- Stage fixes from fresh editor content and current exact runtime/package identity. Preserve timing metadata, lyrics, media, controls, links, publicity, accessibility and approved choreography. Metadata-only input repairs do not authorise new rhythmic choreography. Keep staged, awaiting_publication_approval, published and verified_live states separate; obtain the existing exact-payload/action-time confirmation before public saves or plugin installation. Reconcile release-local mirrors and generator inputs after publication, and do not republish passing pages.
- Store project sources, candidates, preview assets, screenshots, evidence, reports, build caches and temporary outputs under `Z:\My Songs`. Publish reusable tool/workflow improvements to their established GitHub repositories and matching releases during the same job, preserving the separate public-deployment gate.
