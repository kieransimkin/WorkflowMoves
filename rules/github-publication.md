## Push project updates to GitHub before hand-off

- Standing instruction from Kieran, 11 October 2026: always push completed project source, tool, skill and workflow updates to their established GitHub repository during the same job. Local edits, staged files, commits and version bumps are incomplete until the remote branch contains the exact validated changes and its commit identity has been read back. Apply to every project chat, task, scheduled job and automation.
- Before changing a Git checkout, inspect its branch, remote, staged and unstaged changes and relevant ownership records. Preserve unrelated work. Use an isolated branch or checkout when ownership is mixed; never push another owner's changes, private song material, credentials, personal data or rights records merely to empty a dirty working tree.
- Before hand-off, reconcile the job's changed paths with the pushed commit, PR and required checks. Follow the existing owned-PR merge, matching-release and registry-publication rules where applicable. A push is not proof of a merge, release or registry acceptance.
- If no appropriate repository exists, resolve a suitable GitHub destination within the authorised scope before treating reusable source or workflow updates as finished. Keep private operational records separate from publishable source. For a genuine access, ownership, privacy or validation blocker, preserve the reviewed candidate and record the exact unpushed paths, reason and smallest remaining action; do not call the update complete or silently carry it into another job.
- When finding older local changes, compare them with current remote source and published releases. Identify already-published equivalents, genuinely unpublished work and unresolved ownership separately. Never reset, discard or blindly publish an old mixed working tree.
